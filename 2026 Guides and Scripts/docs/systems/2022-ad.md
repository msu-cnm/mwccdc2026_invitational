## Initial checks and system-specific security

Inspect `Get-Service DNS,NTDS,Netlogon,Kdc,W32Time`, `Get-NetIPConfiguration`, `Get-DnsServerZone` and, if available, `dcdiag /test:DNS`. Discover the real domain, sites, DNS forwarders, time hierarchy and clients. Preserve AD-integrated DNS, SYSVOL/NETLOGON shares, Kerberos, LDAP, RPC and SMB dependencies. Do not apply workstation local-account or domain-controller hardening templates indiscriminately.

Review privileged groups with the installed AD module, GPO links, recent account/group events and scheduled tasks. Back up affected GPOs with `Backup-GPO` and use supported system-state recovery planning before directory changes; the auditpol backup is not an AD backup. Do not delete/rename users or rotate service-account passwords without updating applications and PCR. Test an owned domain login, DNS resolution (UDP and TCP) and mail/application domain authentication. Check replication only if peers actually exist. Watch lockouts and time skew. GPO may override local audit policy; coordinate domain policy changes rather than fighting automatic refresh.

The [prior-year password-reset review](../prior-year-review.md) explains why `BulkADPasswordChange.ps1` needs adaptation: plaintext password output, partial-reset recovery and PCR coordination must be addressed before use.

## Scripts and reversible changes

From the repository root in PowerShell (elevate for application):

```powershell
.\scripts\windows_guard.ps1 -Action Assess
.\scripts\windows_guard.ps1 -Action Harden
# Use an existing operator-only directory and a fresh filename:
.\scripts\windows_guard.ps1 -Action Harden -Apply -Backup C:\Secure\audit-before.csv
.\scripts\windows_guard.ps1 -Action Rollback -Backup C:\Secure\audit-before.csv
.\scripts\windows_guard.ps1 -Action Rollback -Apply -Backup C:\Secure\audit-before.csv
```

Harden enables only success/failure Logon auditing. It backs up the full audit policy; rollback restores that full policy and may overwrite later audit changes. Coordinate with other operators and GPO before rollback. Repeat application to the same backup path is rejected. Restrict the backup directory's ACL to operators and SYSTEM. Increased audit volume can fill logs: monitor retention and disk use. Assess exports event counts rather than raw credential-bearing messages; unavailable event access can produce empty counts, which is not proof of no incidents. The script does not change firewall, accounts or services.

## Vulnerabilities and applicability

Run read-only discovery in an elevated PowerShell session; reading Security logs requires administrative/Event Log Readers access and some AD/SQL queries require additional delegated rights. Keep output in an operator-only directory, with UTC timestamps and no passwords. An access-denied error or empty log is a collection gap.

```powershell
Get-ComputerInfo | Select-Object WindowsProductName,WindowsVersion,OsBuildNumber,OsArchitecture
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion' |
  Select-Object ProductName,DisplayVersion,CurrentBuild,UBR,EditionID
Get-HotFix | Sort-Object InstalledOn -Descending | Select-Object -First 15
Get-WindowsPackage -Online | Where-Object PackageState -eq Installed |
  Select-Object PackageName,ReleaseType,InstallTime
Get-NetTCPConnection -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess
auditpol /get /category:* /r
```

`Get-HotFix` alone is not a complete servicing inventory; compare build/revision and installed packages with release history, the exact KB prerequisites/known issues and Microsoft Security Update Guide product filters. A product name or old-looking version is possible exposure, not a confirmed CVE. These guides deliberately do not infer a CVE or fixed build from the packet.

1. **Unpatched DC components.** Record Server 2022 build, running roles (`Get-WindowsFeature | Where-Object Installed`) and matching update applicability. A missing applicable security KB with its affected component enabled is actionable evidence; packet OS alone is not. Install the supported cumulative/security update after prerequisite and known-issue review. While deferred, retain public scoring, DNS/Kerberos/LDAP/RPC/SMB and official access; reduce only a proven unnecessary component or confirmed malicious source after dependency testing. Watch new remote logons, unexpected services and crashes in Security/System; 4688 needs extra auditing. These indicators are not specific proof of a particular vulnerability.
2. **Privileged identities/GPO or directory persistence.** Discover domain with `Get-ADDomain`, enumerate `Get-ADGroupMember 'Domain Admins'`, `'Enterprise Admins'` in the forest root if applicable, and `Get-GPO -All`. Review delegation, AdminSDHolder ACL and GPO ownership against approved operators. An unexpected principal with effective write/replication rights is a misconfiguration; validate inherited permissions before remedy. Export affected GPO/ACL evidence, remove only the confirmed unauthorized grant and restore an approved policy. While deferred, monitor those objects and affected accounts; do not blanket-reset users or break service identities. Indicators: unapproved 4728/4732/4756 membership and 5136 object changes. Audit Security Group Management and Directory Service Changes plus matching object SACLs are required; GPO file changes also need SYSVOL evidence.
3. **LDAP/SMB/legacy authentication exposure.** Read `Get-SmbServerConfiguration | Select EnableSMB1Protocol,RequireSecuritySignature,EnableSecuritySignature`; inspect DC LDAP-signing GPO and client compatibility, not just registry defaults. Cleartext/unsigned binds and unsigned SMB where authentication is used establish exposure, not confirmed relay. Stage signed LDAP/SMB and supported TLS after testing mail/app clients; do not disable NTLM or change Kerberos policy indiscriminately. While deferred, retain required public/general access, remove only unused legacy features after testing and alert on new authentication sources. Directory Service 2887 summarizes unsigned binds; 2889 needs LDAP Interface Events diagnostic level 2 (separate, approved change). Security 4768/4769/4771 require Kerberos Authentication Service/Service Ticket Operations; 4776 requires Credential Validation. Unexpected RC4 or failures may reflect old clients/time skew rather than compromise.

## Patching and recovery

1. Discover builds/roles, time (`w32tm /query /status`), DC health (`dcdiag /test:DNS`) and, only with peers, `repadmin /replsummary`. Record public DNS, owned domain-login and mail/app baselines with dependency owners.
2. Obtain a supported system-state backup using the existing approved Windows Server Backup process, GPO backups and protected DNS/configuration exports. Confirm backup completion, restore access/DSRM credentials and a rehearsed Microsoft forest/DC recovery plan; audit-policy CSV and snapshots are not substitutes.
3. Preview the exact KB in Windows Update/approved update tooling without installing; compare applicable products, prerequisites, architecture, servicing stack and known issues. Plan one DC at a time if redundancy exists; assume an outage if it does not.
4. Manually install the selected signed Microsoft update with an agreed maintenance window. Do not enable unattended fleet upgrades. Let the installer determine restart requirements; schedule the reboot with dependent hosts and keep NETLAB console open. Do not repeatedly restart NTDS or kill servicing processes.
5. Recheck build/update status, DNS UDP/TCP, SYSVOL/NETLOGON, time, replication if present, real domain login and downstream SQL/mail/application workflows, ICMP and Quotient.
6. On failure preserve event/servicing evidence and restore only a reversible policy change first. Updates may not be uninstallable; use the exact KB's supported recovery or tested system-state/DC recovery with staff and dependency owners. Do not perform casual authoritative restores, clone a DC, reset KRBTGT twice or reset every account. Recheck scoring after recovery.

## Detection when patching is deferred

The repository's `windows_guard.ps1` enables **only Logon success/failure auditing** (typically 4624/4625); it does not enable every event below. Inspect effective policy with `auditpol`, log retention with `Get-WinEvent -ListLog Security,System`, and GPO ownership before requesting extra auditing. Account Management is required for 4720/4728/4732/4756; Special Logon for 4672; Security System Extension for 4697; Other Object Access Events for 4698/4702; Process Creation for 4688, with a separate policy for command lines. System 7045 is a separate service-install source. PowerShell 4104 requires Script Block Logging in `Microsoft-Windows-PowerShell/Operational`; Sysmon is optional and not presumed installed. Audit increases volume and may record secrets: protect exports, size retention and coordinate configuration changes. No event proves a malicious actor without context.

Replication-access indicators require **Audit Directory Service Access** and an appropriate domain-root SACL; 4662 alone is broad. Inspect rights GUIDs for Replicating Directory Changes (`1131f6aa-9c07-11d1-f79f-00c04fc2dcd2`) and Replicating Directory Changes All (`1131f6ad-9c07-11d1-f79f-00c04fc2dcd2`) with Control Access (0x100). A non-DC account/host exercising replication is a lead; approved backup/identity synchronization accounts can legitimately do this. Validate principal and source with 4624 and directory permissions. Baseline peers first; absence of 4662 without SACLs cannot exclude credential replication theft.

## Threat hunting

The event queries below cap returned records with `-MaxEvents`. If the cap is reached, subdivide the 30-minute window with explicit `StartTime` and `EndTime` to avoid hiding earlier activity. Current account/service/task inventories are present-state evidence, not a history of the entire window.

Use a bounded 30-minute window (extend explicitly for an incident). `Select-Object -First` limits displayed records, not the retained log. Review full protected events only for chosen leads.

```powershell
$since=(Get-Date).AddMinutes(-30)
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4720,4728,4732,4756,5136;StartTime=$since} -MaxEvents 200 |
  Select-Object TimeCreated,Id,Message
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4662,4624;StartTime=$since} -MaxEvents 200 |
  Select-Object TimeCreated,Id,Message
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4768,4769,4771,4776;StartTime=$since} -MaxEvents 200 |
  Select-Object TimeCreated,Id,Message
Get-WinEvent -FilterHashtable @{LogName='Directory Service';Id=2887,2888,2889;StartTime=$since} -MaxEvents 100 |
  Select-Object TimeCreated,Id,Message
```

- **Hypothesis: an attacker created directory persistence.** Use the first query, then `Get-ADGroupMember 'Domain Admins'` and `Get-GPO -All | Select DisplayName,ModificationTime,Id`; investigate changed policy links/privileged membership against the baseline. Legitimate injects/admin changes can match. Confirm actor/session and obtain owner approval before restoring a specific ACL/GPO; preserve the original object evidence.
- **Hypothesis: an unauthorized identity read replication secrets.** Use the second query, inspect 4662 rights above and correlate subject LogonId to 4624, source host and approved replication principals. Backup/sync agents may be benign. Follow up with delegated AD ACL review and affected credential scope; avoid blanket resets.
- **Hypothesis: password spraying, ticket abuse or relay-compatible clients.** Use third/fourth queries, compare account/source failures, subsequent successes and ticket service/encryption patterns. Batch services, clock skew and old clients explain noise. Check time, client owner and relevant LDAP/SMB policy; investigate the source locally and stage compatibility fixes rather than disconnecting authentication dependencies.

## Splunk monitoring

For installation, input configuration, validation and rollback for this host, use [concrete data-source setup](../splunk-data-sources.md).

Map `index=REPLACE_WINDOWS`, `host="REPLACE_LIVE_HOST"` and `sourcetype="REPLACE_SECURITY"` to discovered inputs first; topology IDs are inventory keys, not verified hostnames. This example assumes XML Security events and extracted `EventCode`, `SubjectUserName`, `TargetUserName`, `IpAddress`; map `EventID` or vendor add-on fields if necessary. Start with `index=REPLACE_WINDOWS host="REPLACE_LIVE_HOST" earliest=-30m latest=now | table _time source sourcetype _raw` to verify ingestion and fields. A zero-result detection with no matching raw records is unknown coverage. See [shared collection, tuning and evidence guide](../splunk-threat-hunting.md).

Available only if collected: Security Logon and System/Directory Service records. Optional prerequisites above supply group, ticket, object and replication events. Windows forwarding/WEF or an existing approved forwarder can collect them; no agent installation is assumed.

```spl
index=REPLACE_WINDOWS host="REPLACE_LIVE_HOST" sourcetype="REPLACE_SECURITY" earliest=-30m latest=now
(EventCode=4728 OR EventCode=4732 OR EventCode=4756 OR EventCode=5136 OR EventCode=4662)
| table _time EventCode SubjectUserName TargetUserName ObjectName Properties IpAddress
| sort 0 - _time
```

For `2022-ad`, expect a bounded timeline of directory/group activity. Inspect raw XML for missing object/GUID fields, resolve account SIDs and compare changes with approved administration and replication peers. 4662 requires the rights/SACL analysis above; this search is a triage queue, not an automatic compromise verdict. Keep local EVTX and GPO evidence independently if Splunk is suspect.
